# Win-CodexBar + Mobile Connect v0.71.1

Gemini Apps now keeps its login in a dedicated persistent browser. PC quota history survives refreshes and restarts, appears in the selected-provider view with **7 days / 30 days**, and supplies the same observations to paired phones and tablets.

## Changes

- Keep Google login, cookies and device keys inside a dedicated WebView2 profile. Updating the EXE retains the selected profile and Mobile Connect pairing. The official Gemini app does not have to stay open.
- Add explicit browser and profile import, including Vivaldi. A failed import retains the previous connection. Exported cookies can still expire; a locked database asks the user to close that browser once.
- Resume unfinished dedicated sign-in after restart. After two-step verification, **Finish connecting** can return a stuck Google page to Gemini in the same profile and verifies quota before replacing the saved connection.
- Fix restored chart history being cut to 56 samples on the next forecast refresh, which could leave about one hour at a one-minute refresh interval.
- Retain the PC's encrypted account/connection archives for up to 90 days. Keep first/latest real observations per ten-minute bucket, including recent reset boundaries. Under capacity pressure, older records are summarized daily while recent records remain detailed. Checkpoints are bounded to the startup reader's size limit and saved atomically.
- Show the last 7/30 days from that archive on Windows; the unchanged Android protocol exports the same canonical last-30-day series. Recording continues with sharing off. Unknown accounts are not merged, missing periods are not invented, and data never collected in the past cannot be reconstructed.
- Publish provider update events after the history checkpoint. The archive uses observation bars rather than inferred connecting lines, so sampled-away resets and offline periods do not appear as continuous usage.
- Port compatible upstream Windows updater execution-policy and Korean notification fixes. Android source and APK are unchanged in this update.

## Update

Download **Win-CodexBar-Mobile-Connect.exe**, exit the resident app, replace the EXE and start it. Keep the existing Windows user and app data directory. Settings, encrypted connections, the dedicated Gemini browser and pairing stay in place. Windows 10/11 x64 and WebView2 Runtime are required. The EXE is **unsigned**; SHA256SUMS and build-provenance.json identify the exact artifact and source.

### Source and restart checks

The PC was then updated to the exact downloaded release EXE above, preserving the same settings, encrypted Gemini selection and Mobile Connect pairing. A backup of the previous EXE and full app data was retained locally. Matching provider/account-scope/window identities allowed recovery of 610 real observations from an older local store (392 Antigravity, 120 Claude, 98 Codex), with zero conflicting values; encrypted roundtrip and a second zero-addition merge were checked first. No accounts were combined and the old store was left intact.

On the published EXE, the native history getter and authenticated mobile snapshot agreed on Gemini's 60 observations and Codex's 64-point projection. Codex's oldest displayed point was 2026-10-17 05:40 JST, over 27 hours before collection. A further controlled termination/restart of the published EXE retained these archives and obtained fresh Gemini quota from the same selected login without reauthentication. The installed/running process hash matched the published EXE; proof mode and temporary debugging were off afterward (no listeners on the two verification ports).

A direct read of the actual encrypted store after that restart retained Codex's 137 stored observations and Gemini's 60, with both oldest timestamps unchanged. The 64-point Codex mobile/desktop projection is a bounded view of those records, not the storage limit. Records absent from every earlier store cannot be reconstructed.

The source passed [Windows CI 39079106094](https://github.com/lingmulongtai/Win-CodexBar-Mobile-Connect/actions/runs/39079106094): 4,853 core tests (two existing ignored tests), 782 desktop tests, one CLI test, 1,347 frontend tests across all 144 files, workspace Clippy with warnings denied, frontend lint/build, locale parity and the portable EXE build. Frontend lint retains 11 existing warnings and no errors. Source regressions cover loaded history followed by refresh, 30-day restore followed by another collection, encrypted checkpoints, reset boundaries, maximum archive capacity and account/stale-request isolation.

The immutable release source is main merge `0c421787df66f61b0ea0e7c9bcfe5260227512ca`, tagged `v0.71.1`. A fresh local Tauri debug build also passed. Actual Windows WebView2/CDP checks rejected an unscoped history request, then verified anonymous demo UI switching from 32 observation bars at seven days to 128 at thirty days, without inferred connecting lines. Demo UI data is supplied for illustration and does not establish historical live acquisition.

Before publication, an in-place local-build upgrade on the user's PC retained the settings, encrypted Gemini selection and pairing files byte-for-byte, after backing up the previous EXE and app data. Fresh real Gemini quota remained bound to the same selected browser. The native archive getter and authenticated paired-device snapshot agreed on Gemini's 54 observations and Codex's 36. A controlled process termination and restart then restored the archive and collected again (Gemini 56, Codex 37), with no Google sign-in and with the temporary debugging port closed. These are bounded update/restart checks, not a multi-day live measurement.

The separate scheduled recorder was stopped and removed at the user's request because it displayed intrusive console windows. This release does not install a recorder task. The earlier short live observation and current successful quota reads do not establish 24-hour or indefinite authentication stability. Google can revoke a login or require user sign-in again.

The Windows native capture helper timed out after retry and reinitialization. Real WebView2/CDP checks and captures are recorded separately from native frame/tray verification; no claim is made that native-frame screenshots were obtained this time.
